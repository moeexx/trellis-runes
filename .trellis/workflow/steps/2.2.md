# 2.2 质量检查 `[required · repeatable]`

## 目标

对照规划产物、spec 和实际 diff 检查实现，并直接修复发现的问题。极简档不强制派发 `trellis-check`，但仍需自行确认相关测试/lint 通过后再收尾。

## 执行动作

所有 check mode 的报告必须写明检查范围、实际执行的命令及结果、P0/P1/P2 findings（没有则写 `none`）、修复或阻塞原因，以及可复核的文件/命令证据。不得静默跳过检查；任何 `skipped`、失败或无法执行的层级必须说明原因、影响和下一步。

- review：报告覆盖的 diff、PRD/spec 对照结果，以及是否触发 SQL review。
- unit-test：报告每个 unit 命令与结果；失败时停止，不得继续宣称更高层验证通过。
- integration-test：报告 API/E2E 命令、依赖环境和结果；只在要求的低层验证已通过后执行。

具备 sub-agent 支持的平台派发 `trellis-check`：

- prompt 必须以 `Active task: <task path>` 开头。
- 明确 agent 已是 `trellis-check`，不得再次派发 check/implement agent。
- 检查所有代码改动、跨层数据流、测试和相关 spec。
- 发现问题时直接修复并重新验证。

高风险完整档可在检查后可选派发只读 `verify`，由主会话比较派发前后的 `git status --porcelain`；发生写入则结果作废并重审。普通档和极简档不派发该角色。

最后一轮检查（提交前）必须使用 `get_context.py --mode packages` 确认受影响 package，并读取对应 spec index 的 Quality Check。

## 产物与状态

- 检查问题已修复，或明确记录无法修复的阻塞项。
- lint、type-check、相关测试和跨层检查已完成。

## 验证标准

- 质量检查通过。
- 没有遗漏相关 package、平台入口或生成模板。
